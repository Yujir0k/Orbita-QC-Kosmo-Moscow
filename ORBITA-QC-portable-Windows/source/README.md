# ОРБИТА.QC — исходный код

React 19, TypeScript strict, Vite 6. Новых production-зависимостей нет.

## Запуск и пересборка

```powershell
pnpm install --frozen-lockfile
pnpm data:sync
pnpm dev
pnpm test
pnpm build:portable
```

`data:sync` читает `../../quality_dataset/expanded_dataset`: 180 изделий, справочники, индекс 8 фото и **только** `events/source_deliveries.jsonl`. Скрипт создаёт `src/demo-data.json`, реальные изображения в `public/media/` и копии внешнего и ошибочного потоков в `public/demo/`. План контроля и проектные интеграционные профили хранятся отдельно в `src/config.json`. Старый набор из 12 изделий не импортируется повторно. Файлы `expected/*` и `interactions/scripted_actions.jsonl` не являются входом приложения.

`pnpm build:portable` выполняет строгую проверку типов, Vite-сборку и переносит `dist/` в `../site/`. Для обновления итогового архива из этой папки запустите `python scripts/package-windows.py`: скрипт создаст `../../ORBITA-QC-workspaces-Windows.zip` с переносимым приложением и расширенным набором данных. Для запуска готовой версии используйте `../START.cmd`.

## Работа демо

- При первом открытии приложение принимает внешний поток до первого сигнала или невозможности оценки для каждого проблемного изделия. Обычные изделия проходят автоматически. Последующие внешние операции этих изделий остаются в ожидании действия роли.
- Администратор → «Поток событий» → «Сценарии и воспроизведение» управляет загрузкой встроенного набора, паузой, следующим шагом, продолжением, сбросом и импортом JSON/JSONL. «Качество данных» отдельно показывает результаты приёма. «Проверить ошибочный поток» берёт из `ingest_stream.jsonl` только намеренно ошибочные доставки.
- Контролёр работает в трёхколоночном кокпите: очередь, исходные кадры и досье с закреплённым пультом решения. Доступны фильтры, сравнение кадров, проверка SHA-256 файлов, клавиши F1–F4, пробел и Z. Если фото, замера, документа или реквизита нет в источнике, соответствующее поле остаётся пустым; решение по непригодному кадру блокируется. Мастер фиксирует работу с исполнителем и комментарием; в опорных сценариях соответствующее учебное фото прикрепляется автоматически. Технолог записывает гипотезу или заключение о допустимости. После работы мастера выпуск оформляет контролёр.
- События и решения сохраняются в `localStorage` данного браузера. Переключение роли и обновление страницы их не стирает. «Сбросить» возвращает исходное демосостояние.
- Фото представлены синтетическими учебными материалами. Фото ITEM-013 не заменяет ручной замер: значение, прибор и подтверждение поверки контролёр вводит при решении о выпуске. У ITEM-015 до действия мастера кадр отсутствует. Цифровая подпись, хеш-цепочка и обмен с ERP остаются не подключены.

## Основные файлы

| Путь | Назначение |
| --- | --- |
| `src/domain.ts` | Валидация и приём, дедупликация, поздние события, хранилище, шаги сценария, действия ролей и проекции |

| `src/live-views.tsx` | Умная очередь с фильтрами и панель воспроизведения внутри прежних рабочих экранов |
| `src/dialogs.tsx` | Паспорт, отдельные состояния процесса, фото, история и формы действий |
| `src/views.tsx` | Исходные ролевые главные экраны с планетой, карточки и все рабочие разделы; текущие проекции и проектные разделы |
| `src/navigation.ts` | Роли, разделы и адреса |
| `tests/foundation.test.cjs` | Сквозные проверки ITEM-013–016 и ITEM-018, маршрутов и ошибок приёма |

## Границы реализации

Это локальная демонстрация. Приём файлов, поток, действия и показатели работают в браузере; общая серверная база и авторизация пользователей отсутствуют. Переключение роли показывает рабочий процесс, но не обеспечивает защиту прав. Подключения к ERP/MES/КОМПАС-3D, внешняя CV-модель, криптографическое хранилище и сетевой обмен остаются проектными разделами. `localStorage` не является неизменяемым производственным журналом.
